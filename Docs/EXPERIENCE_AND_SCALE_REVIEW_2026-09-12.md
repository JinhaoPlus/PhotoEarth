**Photo Earth：体验、交互、情绪价值与大图库审查（2026-09-12）**

这轮最值得追求的结果，是让用户更快看到自己的世界、更自然地连续观看照片，并让旧旅行和深层照片始终容易找到。现有地球构图、原生侧边栏、直接操控和分页基础已经成立；下一轮工作的重心应放在体验连续性、范围表达与累计计算成本。

本文是基于当前工作区的审查建议，尚未成为新的产品约定。涉及交互变化时，文中明确指出与现行约定的关系。审查没有改动产品源代码或用户图库。

审查覆盖了当前导航、首页、扫描、地球、照片墙、详情、PhotoKit 图片链路、SQLite 查询和流式聚类。重新构建并运行了一条现有完整 UI 流程，检查了四张 1920 × 1080 模拟器截图；另用公开示例及合成数据做了 SQL 与纯 Swift 探针。模拟器流程通过，证明该路径可用；本轮没有 Apple TV 真机帧时间、实体 clickpad 手感或真实 iCloud 弱网测量。

**1. 先让“这次中键会打开什么”一眼可知。**

当前有两个合理但不同的规则：从首页主入口进入，照片墙读取点击瞬间的可见地表；从城市卡或照片地点进入，照片墙固定该城市的地点成员。第二种规则保护城市归属，符合已经确认的要求。

问题在于探索界面没有表达这个区别。`enterExplore` 保留 `exploreCity`，`openPhotoWall` 继续使用它；拖动地球没有解除城市限定。同时底部胶片仍按新的当前视野查询，操作文案仍是通用的查看照片。用户从东京出发，转到别处后，可能看到另一片区域的预览，却再次打开东京照片。这是现行规则缺少可见提示，并非建议通过拖动偷偷改变范围。[范围状态](../PhotoEarth/Features/Globe/GlobeView.swift)、[探索提示](../PhotoEarth/Features/Globe/GlobeExploreChrome.swift)

建议城市模式保留一个克制的范围提示，例如“东京 · 仅看此城”，并在现有长按工具条内提供显式“改看当前画面”。切换仍使用工具条的原生 Focus，普通拖动场景保持直接操控。城市模式的胶片建议只取“屏内真实坐标 ∩ 当前城市成员”，使预览与中键目的地保持一致；如果采用这一调整，需要同步更新城市模式胶片约定与测试。

还应区分“没有选出预览”和“区域内确实没有照片”。胶片只抽样最多 144 条候选，查询失败也可能被上层转成空数组，因此它的空结果不能证明照片墙为空。建议改成“暂未找到预览 · 中键查看照片”，并区分服务错误、查找中和严格计数后的空结果。[胶片空状态](../PhotoEarth/Features/Globe/MemoryPhotoStrip.swift)、[查询错误路径](../PhotoEarth/App/AppModel.swift)

验收应覆盖：从城市进入后跨区域拖动、中键打开仍保持城市限定；用户显式切换后按冻结投影取照；地名未知和无预览时不会误报没有记忆。

**2. 把详情页做成可以停留、可以连续观看的场景。**

`PhotoDetailView` 只接受一条记录，没有上一张、下一张或当前集合的浏览游标。当前用户看完一张，需要返回照片墙、移动焦点、再次打开。几十张照片会把这种中断重复几十次。[详情实现](../PhotoEarth/Features/PhotoViewer/PhotoDetailView.swift)

建议纯照片状态下左右切换同一冻结集合中的前后照片；中键展开安静的操作层，操作层出现时方向键交给标准 Focus。按 Back 保持现有“详情 → 原照片墙”的层级，并恢复最后实际观看的那张照片。连续翻页必须跨越第 48/49 张等分页边界，采用有限邻图预取，不能预先把整个集合的资产 ID 和大图加载到内存。

本轮详情截图中，顶部两个大按钮、左下约 320 × 340 pt 的地球卡，以及打开后的 500 pt 信息面板共同占据注意力；小地图覆盖了原照片左下的建筑。信息面板本身清晰，但“观看照片”和“查看信息”需要更明确的节奏。

建议进入详情先显示继承自照片墙的预览，随后升级适屏清晰图。操作层短暂出现后退场；小地图随操作层或信息面板出现。收起时恢复完整照片构图，不加自动裁切、持续推拉或默认 Ken Burns。用户正聚焦按钮、操作面板、等待重试，或使用 VoiceOver 时，不能靠定时器隐藏其焦点目标。右侧面板和地图入口继续可达。

这会调整当前“小地图常驻详情”的显示方式，属于产品改动建议；照片地点、导航目的地与原始比例规则继续保留。小地图只在需要时创建，并在同一详情会话中按照片更新，可同时减少额外 MapKit 实例创建。主地图仍保留冻结实例，保证返回的投影与相机连续。

Apple 的 tvOS 指南强调远距离可读、边到边内容与电影感；Focus 指南强调用户应始终知道焦点位置。这支持“安静观看 + 明确的操作状态”，不支持悄悄挪走正在操作的焦点。[Apple tvOS 设计](https://developer.apple.com/design/human-interface-guidelines/designing-for-tvos)、[Focus 与选择](https://developer.apple.com/design/human-interface-guidelines/focus-and-selection)

**3. 让第一次情绪回报发生在地名补全之前。**

现有扫描页已经有“现在开始探索”，并且后台工作不会因为关闭扫描页而停止。剩余问题是默认路径：自动关闭扫描页仍以初次准备进入 `.complete` 为条件；索引提交时，`applyPreparedIndex` 保持 `.scanning`。部分结果、地理服务冷却或大量地名查询，会让用户继续停在准备页，虽然可浏览内容已经存在。[准备交接](../PhotoEarth/App/AppModel.swift)、[地名工作循环](../PhotoEarth/Services/PhotoLibrary/LibraryPreparationCoordinator.swift)

建议把“地球可以浏览”和“地名全部完成”分成两个里程碑。首个有效元数据索引原子提交后，给一次简短完成反馈，自动进入同一张地球；地名继续在前台后台任务中补全，进度入口沿用现有设计。若用户正在操作暂停或查看进度，则保持其当前位置，由其主动进入。可读但无定位照片的空库应进入明确空状态。

完成反馈使用实际得到的地点或年份信息，允许匿名地点。不要为每个地名再完成一次而重播开场，也不要把 MapKit 的 `fullyRendered` 当成高分辨率影像已到达的证明。“等待地球影像”继续保留超时降级，默认开关的改变需另行评估。

欢迎页目前仍以渐变圆和七个装饰点作主视觉，字体也更偏模板式大标题。它可以复用已经存在的 MapKit 地球背景与首页字体语言，让权限说明之前的第一眼就呈现产品本身。未授权时使用中性地球或明确标注的公开示例，不制造属于用户的虚假光点。[欢迎页](../PhotoEarth/Features/Onboarding/WelcomeView.swift)

**4. 光点的名额应服务于当前正在看的世界。**

现有 LOD 按所有地点的最近到访时间排序，再按每个 2° 网格最多两个、全局最多 180 个截断。它不接收镜头参数；Coordinator 只在内容修订时更新这组选点。缩放改变标注外观，并不会找回未被选中的旧地点。[选点算法](../PhotoEarth/Rendering/Earth/MapKitEarthView.swift)

本轮直接提取现有 `MapPlaceLOD`，使用 180 个较新、分布在不同网格的地点，加一个另一大陆的旧地点：输出 180 个，旧地点被排除。因为普通相机移动不触发重新选择，转到旧地点所在区域也不能凭这次转动恢复它。照片记录并没有丢失，但用户更难发现那里有自己的记忆。

建议在索引变化时构建轻量的地点空间桶。停稳或跨过较大的视野/尺度阈值时，先筛视野相关的桶，再分配最多 180 个光点；世界尺度优先地理覆盖，区域尺度优先当地可见地点，照片定位产生的临时标记继续优先保留。更新采用增删差量及阈值滞回，避免边缘光点频繁跳动。

这里处理的是应用的地点标记索引，不接管 MapKit 的影像、地形或地图瓦片。地点内容签名仍只在索引变化时计算，不能为了视野适配回到每帧全库排序。验收重点是大量近期地点存在时，旧大陆仍能被发现，密集区域数量仍有硬上限。

**5. 照片墙最值得先优化的是总工作量。**

`readPhotoPage` 的 SQL 使用 RTree 连接后按时间与 ID 排序，再执行 `LIMIT 513 OFFSET ?`。限制了返回和解码数量，但数据库可能重新访问、排序整个矩形候选集。`PhotoWallTotalSelection.count` 为准确总数重复这一过程；分页浏览还会再次访问其中的部分候选。当前首屏已经先展示、总数异步统计，因此不能把下面的全遍历耗时写成开墙等待时间。[空间分页 SQL](../PhotoEarth/Services/Persistence/TravelIndexStore.swift)、[精确计数](../PhotoEarth/Domain/Models/PhotoWallSelection.swift)

本轮合成基准使用 macOS 26.6.2 arm64、Python SQLite 3.51.0，与生产一致的照片索引和 RTree 查询形状。80% 记录集中于一个区域、其余分散全球，查询大范围矩形；包含同时间记录。每种全遍历执行三次，以中位数报告。两种路径的返回数量与全部有序 ID 的 SHA-256 完全一致。没有访问私人 SQLite，也没有调用 PhotoKit 或 MapKit。

| 合成记录数 | 矩形候选数 | 当前 OFFSET 分批遍历 | 单一 SQL 游标，按 512 条步进 | 当前单批首段／末段中位数 |
| --- | ---: | ---: | ---: | ---: |
| 50,000 | 45,028 | 3.200 秒 | 0.047 秒 | 17.61 / 42.17 ms |
| 200,000 | 180,186 | 101.603 秒 | 0.330 秒 | 164.59 / 327.90 ms |

两组执行计划均出现 `USE TEMP B-TREE FOR ORDER BY`。20 万条是超出当前 5 万张设计基线的扩展压力场景。以上仅测 SQL 候选遍历，单一游标比较也不包含 SwiftUI、严格原生投影、内存测量或电视硬件；不能据此承诺 App 提速某个倍数。主机当时也有其他开发活动，数值应作为方向性证据。

建议分两步实施。先保留快速首屏，准确计数改成 reader 持有的持续 SQL 游标，避免每 512 条重启排序；每批消费后让出执行资源。普通照片分页改用稳定键游标：时间降序、同时间 ID 升序，续读条件必须同时处理两个方向，不能直接套用同方向的二元组比较。当前批次尚未消费的记录要保留，游标只能推进到已检查的位置。

城市／国家墙的 `selected_places` 临时表现在每页删除并重新插入，成员既然由同一个 WAL 快照固定，就应按会话建立一次。单地点查询可评估与排序方向一致的 `(place_id, creation_date DESC, id ASC)` 索引；多地点集合仍需单独分析计划，不能承诺一个索引消除所有排序。

随后再按测量决定是否让分页与计数共享一份临时可见结果索引，以 rowid/稳定顺序保存到可清理的 SQLite 临时空间，避免重复投影，并支持回翻。要继续限制内存、临时磁盘、SQL 排序和 WAL 读租约；一次排序也可能产生较大的内部临时工作区。范围与投影失效时清理整个会话。

SQLite 官方同样说明 OFFSET 的工作量随偏移增大；但键游标不能自动解决 RTree 连接后的排序，优化前后必须比较实际执行计划。[SQLite 滚动窗口查询](https://www.sqlite.org/rowvalue.html#scrolling_window_queries)

**6. 把严格投影的预算从“条数”补充为“时间”。**

现有精确计数在 MainActor 中连续检查最多 512 条之后才 `Task.yield()`。每条可能包含原生相机身份检查、地理筛选、投影和回投；512 次不是稳定的毫秒预算。翻到详情时，墙的计数任务也没有因为详情显示而暂停。[投影快照](../PhotoEarth/Rendering/Earth/MapKitEarthView.swift)、[计数循环](../PhotoEarth/Domain/Models/PhotoWallSelection.swift)、[详情打开路径](../PhotoEarth/Features/Globe/GlobeView.swift)

建议 SQL 的 512 条读取预算继续保留，原生投影另按小时间片处理。可从每片约 2–4 ms 开始真机调参，在批次提交前后检查 generation 和冻结镜头身份。用户移动焦点、请求下一页或打开详情时，让统计让路；回到墙时继续统计。精确总数保持精确，不能用首批 48 张、抽样估计或城市摘要冒充当前投影的总数。

同一镜头内，完全相同的真实 GPS 可以使用有限大小的投影结果缓存，帮助同一机位的大量照片。键必须包含该冻结投影身份；不能将坐标四舍五入成网格后当作精确判断。若要用 SQL 聚合重复坐标计数，也要先验证新增分组开销及删除排除语义。

照片墙在第一批没有命中但还有候选时，会显示“继续寻找”按钮。建议共享的查找工作在有界时间片内继续寻找首个匹配，自动交付第一屏，并保留取消/继续入口。用户不应为了推进数据库游标不断按按钮；也不能改成不可取消的无限循环。

**7. 图片链路需要跨页面统一，现有首页实现是起点。**

首页已经具备后台 PHAsset 查找、同图去重、本地 4 / 网络 2 的并发预算、停留门槛、超时与有限缓存。照片墙、分类、详情仍使用另一套 `PhotoKitImageRequester`：在 MainActor 同步 `fetchAssets`，并直接允许网络访问。胶片也在 MainActor 查资产、逐个发起网络许可请求。[首页请求器](../PhotoEarth/Services/PhotoLibrary/OverviewPhotoKitRequester.swift)、[通用请求器](../PhotoEarth/Services/PhotoLibrary/PhotoLibraryService.swift)、[胶片请求器](../PhotoEarth/Services/PhotoLibrary/MemoryThumbnailStore.swift)

所以“首页已经有预算”还不等于“全 App 已有图片预算”。照片墙背后仍保留其列表，进入详情也只停止地名需求，通用图片组件没有显式使用墙的 `isActive` 退订；实际请求和驻留仍受 SwiftUI 生命周期影响，需要真机观测，而不能假定遮住就停止。

建议复用调度机制，给详情、焦点照片、可见行、邻行明确优先级；底层网络与解码资源统一计费，尺寸策略按场景保持：小封面、中预览、适屏清晰图。不能把首页缩略图的 48 MiB 数值直接当作全屏图片或进程总内存预算。隐藏页面主动退订，近期完成预览可在有限缓存中保留；后台、编辑、删除与权限变化统一失效。

照片墙当前全部按 1200 × 1200 fit 请求，可以根据实际行高、卡宽、显示 scale 与资产比例分档，避免极窄竖图或小卡都请求同样的大规格，同时保留焦点升级机会。细节页优先复用墙预览，邻图只有限预取，正在看的那张优先拿到清晰图。

分类页还有串行“封面 → 等这个地点反查 → 下一封面”的链路。某个地名查询变慢，会推迟后面的最新封面准备；把批量封面与地名任务分开，沿用首页已经验证过的做法即可。[分类准备](../PhotoEarth/Features/Places/PlaceLibraryView.swift)

**8. 深列表要把数据分页、布局工作与用户定位一起优化。**

照片墙使用 LazyVStack 和离屏取消图片，是正确基础。不过每次新增一页，`updateRows` 仍映射全部已读记录、扫描旧行并重建两个字典；焦点变化还对全部记录 `firstIndex`。两个墙的宿主也在追加前重建已加载 ID 的 Set。页面越深，追加一次的 CPU 工作越多。[墙布局](../PhotoEarth/Features/PhotoViewer/ViewportPhotoWall.swift)、[行算法](../PhotoEarth/Domain/Models/PhotoRowLayout.swift)、[集合墙](../PhotoEarth/Features/PhotoViewer/CollectionPhotoWall.swift)

本轮从源文件提取真实 `PhotoRowLayout`，用 Swift `-O` 测量旧行保留加字典重建的局部工作，10 次中位数为：1,000 条约 0.144 ms，10,000 条约 0.869 ms，50,000 条约 4.645 ms。这不是完整 `updateRows` 或 tvOS 滚动测量；它确认增长趋势，也说明此项应排在已证实的 SQL 重复遍历之后。

建议按追加批次维护行结构、ID 集合与位置字典，旧行几何保持稳定。更深浏览可回收远离当前位置的照片记录页，但保留必要的行几何、稳定游标和当前照片锚点，回翻再读取。首页因 Focus 需求保留的 VStack 暂时不要凭经验改回 LazyVStack；只有真机显示全部展开后的 Focus 图或布局超预算，再评估原生 UICollectionView 回收。

易用性上，一万张照片只靠不停向下没有明确终点。建议在照片墙顶部提供按年/月定位的轻量入口，选定后在同一城市或冻结区域范围内 seek；当前范围和时间条件同步显示，总数也必须采用相同条件。照片本身保持稳定倒序与原始比例。地点分类和地名补全也应延用首页的稳定结构策略：用户正在浏览时，文字可以更新，卡片身份、顺序和焦点不能随着每个反查结果跳动。

**9. 电影感最有价值的提升，是让照片形成可理解的章节。**

本轮首页截图中，巨大的地球和紧凑 Dock 已经建立视觉主次。更强的情绪可以来自“第一次去日本”“某年冬天的冰岛”“多年后重返同一座城”这些真实经历的组织。建议在现有首页的后续货架或照片墙入口中，试做一条有明确年份和到访时间的回忆章节；最近抵达继续取最新照片，章节封面可单独考虑收藏、清晰度和内容多样性。

探索截图也暴露了一个可以低成本改善的细节：右上操作提示直接覆盖浅色陆地，部分文字对比不足。保留提示淡出策略，但在提示可见时给文字所在的有限区域增加轻薄衬底或稳定阴影，并在雪地、沙漠、夜面分别检查。局部可读性不应依靠全屏压暗或增加持续模糊来获得。

随后可以沿现有预留语义加入用户主动触发的 Play/Pause 旅行播放。用少量宽景建立地点，给照片足够停留时间，再进入下一段；有界预取和现有稳定页游标支撑播放。优先做到随时暂停、恢复当前照片和正常 Back；音频是可关闭的增强，默认不抢占客厅正在播放的内容。此阶段不需要添加地图连线、地图标签或新的主地球渲染器。

当前流式聚类已经避免单个超大地点的二次复杂度。算法更值得继续提升的是语义：地点是按时间连续片段生成，旅程只按相邻时间不超过五天连接；没有完整考虑返回常驻地、合理移动距离和置信度。地点 ID 又由成员中最小照片 ID 派生，最小成员变动时身份也可能变化。同一输入确定性不等于跨编辑身份稳定。[流式聚类](../PhotoEarth/Domain/Clustering/StreamingTravelClusterer.swift)

在把自动结果命名为正式“旅程”并用于播放前，应分开稳定地理目的地、一次到访和一趟旅程，按成员重叠与时空连续性谨慎匹配旧身份；存在歧义就创建新身份，不能把两个地点强行认作同一个。增量变更可以尝试仅重算受影响片段，但必须向两侧扩展直到聚类状态重新稳定，保留完整重建兜底。常驻地只辅助分段，不静默丢弃其照片。

本轮照片墙示例中反复出现同一张冰岛图片，源于现有示例资源复用，不能作为真实用户图库存在重复照片的证据。章节精选也不应改变“全部照片”的完整性。

**10. 用一个完整的电视场景验收，而不只看平均 FPS。**

建议在最早支持目标 tvOS 的 Apple TV 4K 和用户常用设备上分别测量，使用 Release 优化代码。地图维持最高 30 Hz 相机提交；60 Hz 输出下 Focus 与滚动仍按约 16.7 ms 的帧周期检查，不能将地图上限解释成整个 UI 的目标帧率。[Apple SwiftUI 性能分析](https://developer.apple.com/videos/play/wwdc2025/306/)

| 场景 | 需要回答的问题 |
| --- | --- |
| 5 万定位照片，大多数集中一个区域 | 首屏何时有图、总数何时完成、SQL 与投影各耗时多少 |
| 20 万定位照片的扩展压力场景 | 单批、全计数、临时空间与深翻是否出现超线性增长 |
| 大量近期地点 + 另一大陆的旧旅行 | 转到该大陆后是否有可发现的光点 |
| 进入城市后拖往远处，再中键 | 范围提示、胶片和照片墙是否符合用户预期 |
| 连续看照片，跨第 48/49 张并立即反向 | 同图延续、邻图取消、返回最后观看位置是否正确 |
| 本地与云端混合、慢网、无回调 | 焦点是否等待图片、请求能否超时、关键图是否被饿死 |
| 深翻 20 排后往返，再展开数百地点 | 图片、页记录、Focus 图和内存是否分别趋于稳定 |
| 地名补全、增量扫描与浏览同时进行 | 卡片是否重排、数据库读取是否被统计或重建长时间阻塞 |
| Reduce Motion / Transparency、VoiceOver、长语言文案 | 能否持续知道当前焦点与范围，控件是否可达和可读 |

建议新增或补齐首屏、下一页、精确总数、SQL 语句、投影时间片、图片排队/首图/清晰图和内存高水位的 signpost。日志只记录阶段、计数、耗时与错误类型。除总耗时之外，记录 P95 输入到 Focus 响应、最长主线程占用和总 hitch 时间；不要把云端传输慢混同为输入迟钝。

产品体验可以用一个朴素的目标衡量：第一次使用的人无需口头教学，就能转动地球、理解当前照片范围、调整缩放、连续看几张照片，再回到预期位置。长按缩放提示宜依据是否完成过操作来收敛，而不只是每次进入固定七秒后消失；既有短按/长按语义和全触面拖动保持稳定。
