# Photo Earth 万级图库体验评估 · 2026-11-20

优先改善三个用户时刻：按下放映后看到第一张、地图停稳后看到第一批照片、重开应用后看到自己的旅行。三处都有用户必须等待的全量工作。照片墙首批已经可以与准确计数分开返回，值得沿用。连续翻详情另有两项随到访数和已翻页数增长的主线程工作。

## 数据与测法

- **真实分布。** 只读查询 11 月 19 日的电视索引副本。55,987 项来源资产中，30,520 项进入定位索引，分布于 783 次到访。应用默认隐藏疑似途经后有 30,308 项、627 次到访，其中 523 次达到默认的每次至少 5 项。在按经纬度各取 1° 划分的固定网格中，最密格有 **9,632 项**。该格用于描述密度，实际屏内成员仍由 MapKit 投影决定。[既有真机验收](JOURNEY_REFACTOR_ACCEPTANCE_2026-11-19.md)
- **本轮实测。** Apple M4，tvOS 27.2 Apple TV 4K 模拟器，1080p，Debug。1 万和 5 万组分别用了一个城市内互不相同的真实格式合成坐标、一个到访、100 km 相机和原生普通地图。使用产品 SQLite 读取器和 MapKit 正投影／回投，断言所有记录确实可见。媒体像素与 iCloud 下载没有进入这些计时。模拟器与其他本机任务共享硬件，三轮用于观察量级。[原始计时](../.local-test-data/large-library-audit-20261120/metrics.txt) · [密集视野结果包](../.local-test-data/large-library-audit-20261120/native.xcresult)
- **交互回归。** 在独立模拟器上，29 项地图、规模及分页测试和 2 条 UI 流程通过，覆盖卫星到街区再返回、详情第 48→49→48 张及返回墙上原焦点。UI 使用 Demo 素材，5 万组使用独立合成索引。首轮共享模拟器的测试宿主收到 SIGKILL，以下结论采用独立重跑结果。[交互与规模结果包](../.local-test-data/large-library-audit-20261120/isolated.xcresult)

## 持续转动地球

在独立模拟器窗口挂载产品的 SwiftUI 地球图层，保持方向输入 5 秒，通过真实显示链路驱动原生地图。只在临时工程的 MapKit 相机提交处记录时间。每种到访数各跑一次，依次增加地点，期间共用宿主机和系统瓦片缓存。到访数是传入地球的地点摘要数量，每帧直接操作的标记仍有上限。[相机实测结果包](../.local-test-data/large-library-audit-20261120/motion.xcresult) · [探针源码](../.local-test-data/large-library-audit-20261120/MapReviewAuditProbes.swift.txt)

| 到访数 | 5 秒内相机提交 | 提交间隔中位数 | 提交间隔 P95 | 最长间隔 | 同步 setCamera 耗时 P95 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 50 | 134 | 33.6 ms | 67.2 ms | 151.6 ms | 1.44 ms |
| 783 | 143 | 33.3 ms | 53.9 ms | 159.8 ms | 1.67 ms |
| 3,000 | 143 | 33.3 ms | 49.8 ms | 182.7 ms | 1.63 ms |

三组中位数贴近应用的 30 Hz 提交目标。783 次到访时，两次提交最长相隔约 160 ms，同步调用本身通常很短。地点增加时各指标没有一致的增长趋势，当前证据支持先保留地点预算。在电视上应把输入、主线程提交、GPU 呈现和瓦片绘制放在同一条时间线上归因。模拟器日志有图形管线兼容提示，这组数字仅描述应用提交节奏。

## 用户操作与改进顺序

### 1. 从当前画面开始放映

按下播放后，先复制墙所在的整个 SQLite 主数据库，再以每页最多 48 条重新枚举当前画面、逐项投影并写入第二个临时库。随后才请求首批 3 个候选，串行等缩略图走相似度分析。单张分析预览有 4 秒的等待上限，弱网耗时可能叠加。整库首页入口也先写入选定的所有元数据，省去了当前画面的重新投影。5 万视野中约 3.12 秒已花在墙快照和枚举，尚未读取首张图。[放映入口](../PhotoEarth/App/AppModel.swift) · [选片与首次呈现](../PhotoEarth/Features/Slideshow/EarthSlideshowCoordinator.swift) · [分析预览](../PhotoEarth/Services/PhotoLibrary/PhotoSimilarityAnalyzer.swift)

建议先复用冻结墙已经验证的成员和当前可用预览，让第一个符合选片规则的素材尽早展示，接着从同一读版本补齐可播放范围。整库入口可从同一只读版本先取首个到访页。确保排序与去重规则、返回后的墙范围、权限撤回、删除及排除相册仍生效，并及时释放主索引的 WAL 读事务。改动量较大，验收以按键到首张实际呈现的时间为准，另记等待分析预览和等待适屏图的时长。

### 2. 缩近一座城市，松手后等照片

远景用代表抽样，地点空间索引只在内容版本变更时重建。相机输入经过帧合并。近景停稳则先防抖 850 ms，再读取视野候选，分批让出主线程完成严格投影。预览最多保留 48 张，却和最终图钉及总数一起返回。城市限定也要先从 SQLite 取出地理候选，再在 Swift 中筛选所属到访。每次停稳都可能重新做这笔工作。[相机与标记更新](../PhotoEarth/Rendering/Earth/MapKitEarthView.swift) · [防抖与发布](../PhotoEarth/Features/Globe/GlobeExperienceModel.swift) · [近景整批遍历](../PhotoEarth/Features/PhotoViewer/ViewportPhotoBatch.swift)

建议先发布属于当前镜头、已经严格投影的首批预览，准确总数和最终聚合独立完成。把城市成员限制下推到 SQLite；保留代次检查，用户再次拖动时立即撤销旧批。瓦片也应独立计时，项目历史有一次冷缓存街区道路约 40 秒才出现；样式交接预取依赖快照回调，值得在慢网验证有时限地交回原生地图加载。图钉数量、胶片和打开的照片墙最后必须对得上。改动量中等。[冻结照片墙](../PhotoEarth/Domain/Models/PhotoViewportSnapshot.swift) · [底图交接与冷缓存记录](GLOBE_SCALE_IMPLEMENTATION_2026-11-19.md)

### 3. 重开应用与图库后台同步

有缓存的真实图库仍先构建城市目录，得到目录版本后才判断能否展示已有索引。模拟器对内置 28,096 条城市记录重新读取、解析、归并并建索引，每次 544–583 ms，同一资源对象的第二次读取低于 0.1 ms。这段工作在后台执行，但首页在等它。使用有限照片权限或排除大相册时，还需枚举相关成员并计算范围指纹。[启动条件](../PhotoEarth/App/AppModel.swift) · [目录解析](../PhotoEarth/Services/Geocoding/JourneyCatalogResources.swift) · [范围验证](../PhotoEarth/Services/PhotoLibrary/TravelScanPolicy.swift)

先把经过验证的目录版本与匹配算法版本做成可轻量读取的标识，索引复用时只查标识，需要重新匹配时再加载完整目录。相册或权限范围仍须核实后才显示私人照片。另一项独立成本出现在首页可浏览之后：已保存基线的增量同步先复制全部照片到暂存表，再读取 Photos 变化；即使零变化也比较全表并清空暂存。可对可靠的零变化结果只推进同步状态，并覆盖权限、相册成员、相机证据、目录变化和失效 token。普通增量和每周全量核对应分别验证。两项都能单独交付。[同步协调](../PhotoEarth/Services/PhotoLibrary/LibraryPreparationCoordinator.swift) · [暂存与提交](../PhotoEarth/Services/Persistence/TravelIndexStore.swift)

### 4. 在照片墙深处连续按右键

照片墙按页增量布局，详情通过位置字典定位相邻照片。仍有两笔与用户当前看到的单张照片无关的成本：在分类墙，父视图生成整份到访地名字典，展示详情时还会再生成一次以取当前地名；全屏详情每次选中新照片，隐藏的墙也会滚到对应行。已读记录、去重集合和行位置一直保留到离开墙。图片有缓存上限，这几份元数据按已经翻过的页数增长。[分类墙地名](../PhotoEarth/Features/PhotoViewer/CollectionPhotoWall.swift) · [隐藏墙的滚动与行布局](../PhotoEarth/Features/PhotoViewer/ViewportPhotoWall.swift) · [详情相邻定位](../PhotoEarth/Domain/Models/PhotoBrowsingSession.swift)

建议先按到访 ID 取当前和可见地名，详情翻页只记住返回目标，至少合并同一行的滚动。回墙时一次定位并恢复最后观看照片。先用第 500、5,000 张的连续前进和反向返回测按键到预览、焦点恢复及进程内存，再决定是否引入旧页回收。当前只有跨 48/49 边界的 UI 回归实测，深页累计成本属于代码审查发现。

### 5. 弱网下的首页和城市封面

已经选好的部分封面会先向 Photos 请求当前版本的大图编码数据，再缩到卡片尺寸。本地尝试的时限是 400 ms，允许网络时是 8 秒，之后仍有普通尺寸请求回退。滚动到新行或放弃选片时，网络传输和编码数据会影响第一屏出图速度及峰值内存。可先显示与最终封面同一资产、同一构图的可用缩略图；只为停稳的焦点或确需画质升级的可见卡片拉取更高质量版本。建议按本地命中、iCloud 命中分组测量卡片首次出图、实际下载和取消。这项未做本轮弱网真机验证。[封面请求顺序](../PhotoEarth/Services/PhotoLibrary/OverviewPhotoKitRequester.swift) · [大图解码](../PhotoEarthTopShelfShared/CoverOriginalImageRequest.swift)

## 真机验收重点

用 Release 在同一台电视、同一范围分开记录持续转动的实际显示帧间隔、松手到首批图、按键到可辨识预览、按播放到首张呈现，以及一小时进程内存高水位。转动记录 P95 与最长帧，并分别跑冷瓦片和已加载地图；翻页各跑本地预览和主要在 iCloud 的素材。固定访问范围和可见总数作为正确性对照。11 月 19 日真机已有一小时呈现 463 个不同素材的记录，当次无线 Instruments 采样中断；它能支持持续推进和去重，仍缺稳定帧率及峰值内存证据。[一小时真机验收](JOURNEY_REFACTOR_ACCEPTANCE_2026-11-19.md)
